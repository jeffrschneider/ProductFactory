PROCESS: make a new agent             id: product-factory/make-a-new-agent   v3
from: ref/dev/make-a-new-agent v1
owner: <who>                          effective: <date>
trigger: a person asks for an agent in words, through
         the Product Factory console, with a prototype attached when one
         exists; or asks for a released agent to differ, with the
         version that runs today attached as the prototype
concurrency: runs may overlap - one run per agent at a time; each feature
             of the version is made in a run of its own, of
             product-factory/make-a-feature v1, and those runs overlap
goal: a running agent whose package was made from a spec the owner
      approved and an architecture record that named and bound every
      system it reaches, whose scripts were made one feature at a time, each
      passing a suite written before it, and
      whose conformance was checked by an agent that did not build it,
      with every step on the record
phases:
  write-the-spec     - harness: the four answers settled and the request
                       turned into a spec, with every blank the request
                       left named. The four are which kind of agent,
                       one agent or several, whether the organization
                       can stand a product behind every system the
                       design names, and whether the thing already
                       exists; each is the person's from a short list,
                       and two of them can end the run
                       owner: spec-writer          after: trigger
                       automation: assisted
  approve-the-spec   - human: the owner reads the spec, answers what it
                       left open, and changes it or says yes
                       owner: <the agent's owner>
                       after: write-the-spec
                       automation: never
  write-the-architecture - harness: the architecture record written from
                       the spec as the owner approved it and the
                       organization's stack: the systems the agent
                       reaches, in plain system words; the product
                       bound to each in dev, test and production, the
                       organization's choice first and the platform's
                       default for the rest; its dependencies, its
                       kind, its limits on cost, speed, data and trust,
                       its egress, and every decision with its reason.
                       What only a person can commit to (a binding
                       nobody chose, a spending limit, a destination
                       beyond the derived set) is asked of the owner,
                       who answers it before the record goes on, and
                       none of it is filled in. The record is set up
                       once for a product and carried forward to its
                       later versions unchanged until someone asks for
                       a change
                       owner: solution-architect   after: approve-the-spec
                       automation: autonomous
  design-the-agent   - harness: the agent's own files made again from the
                       spec as the owner approved it, within the
                       architecture record: exactly the systems the
                       record names, its kind, its formats and its
                       settings, and no product, address or credential
                       owner: spec-writer          after: write-the-architecture
                       automation: autonomous
  gather-the-features - system: every feature approved for the version
                       made in a run of its own, of
                       product-factory/make-a-feature v1, started at the
                       spec's approval or at the feature's own approval
                       after it; once every one of those runs has
                       closed, the scripts as the last feature accepted
                       merged them on the version's base, which passed
                       the whole suite
                       owner: product-factory      after: design-the-agent
                       automation: autonomous
  make-the-package   - harness: the signed Agent Package made from the
                       agent's own files, which the spec writer makes
                       from the spec within the architecture record,
                       and the delivered scripts and
                       nothing else, carrying the draft Descriptor in
                       agent-descriptor.json and the runtime
                       requirements in agent-runtime-requirements.json
                       owner: package-maker        after: gather-the-features
                       automation: autonomous
  approve-the-deploy - human: the owner reads the package's build record
                       and says whether it goes on the host you bring
                       owner: <the agent's owner>
                       after: make-the-package
                       automation: never
  deploy-the-agent   - harness: the package installed on the host you bring,
                       or the running agent updated when the name
                       already runs; the deployment manager answers with
                       the agent's name and the signed deployment record
                       owner: deployment-manager   after: approve-the-deploy
                       automation: autonomous
  check-conformance  - harness: the test derived from the package's own
                       declarations, run against the installed agent,
                       with each case confirmed, failed or flagged
                       owner: conformance-checker  after: deploy-the-agent
                       automation: autonomous
  publish-the-agent  - human: the owner reads the agent's AgentDoc,
                       assembled from the deployed agent's descriptor
                       and the records of the run, and says it may be
                       listed; the listing is made by the platform that
                       hosts your catalog, from the descriptor
                       owner: <the agent's owner>
                       after: check-conformance
                       automation: never
handoffs:
  write-the-spec -> approve-the-spec [spec-drafted]: the spec, the four answers
    as the person settled them, and the list of what the request left
    open
  approve-the-spec -> gather-the-features [approved-spec]: the spec as
    the owner left it, with who approved it and when, which every
    feature's run carries, and the prototype when one came with the
    request
  approve-the-spec -> write-the-architecture / design-the-agent [approved-spec]:
    the spec as the owner left it, which the architecture is written
    from and the agent's own files are made from
  write-the-architecture -> design-the-agent [architecture]: the
    architecture record, with every question it asked answered by the
    owner
  design-the-agent -> gather-the-features / make-the-package [designed]:
    the agent's own files made from the spec within the architecture
    record, which every feature's run carries and which name the
    scripts the package must ship
  gather-the-features -> make-the-package [scripts]: every script the
    spec names, as the last feature accepted left them, with the record
    of each feature's run
  make-the-package -> approve-the-deploy [package]: the package's
    address, its sha256, and the build record
  approve-the-deploy -> deploy-the-agent [approved-package]: the
    package's address and sha256, with who approved it and when
  deploy-the-agent -> check-conformance [agent]: the agent's name and
    the deployment record
  check-conformance -> publish-the-agent [eval-record]: the signed
    evaluation record, every case confirmed, failed or flagged, and the
    AgentDoc's address
deviations:
  approve-the-spec -> write-the-spec [changes]: the owner names what is
    wrong or answers a blank; the spec is revised, not drafted again
  gather-the-features -> approve-the-spec [conflict]: a test of a
    feature's run cannot pass without breaking what the spec says, and
    the owner judges the spec wrong; the spec is revised, and each
    feature's run still open revises its suite against the revised spec
    and goes on
  make-the-package -> gather-the-features [untraced]: a script the
    package would ship cannot be traced to a feature's run; the
    features are gathered again
  check-conformance -> gather-the-features [failed]: a case the
    package's own declarations promise has failed; the features are
    gathered again, and the feature that broke it is made again
  approve-the-deploy -> write-the-spec [wrong-spec]: what was built is
    not what was wanted; the request is restated and the spec redone
bindings:
  roster:  named for each build in the roster Product Factory sends
           with the run: the reference spec writer of CommonAgent/adlc
           for write-the-spec and design-the-agent, the reference
           solution architect of CommonAgent/adlc for
           write-the-architecture, Product Factory itself for
           gather-the-features, the Common Agent packer for
           make-the-package, and the agent's owner (person), who holds the
           three human phases; each feature's run is sent its own roster
  systems: none of the phases reaches a system of its own; each agent
           brings what its package declares
  data:    the request, the prototype when there is one,
           node 22
policy:
  a request for an agent this process cannot make, meaning anything but
    a package a harness reads, is said out loud at the spec and never
    built as something else that looks close
  a spec goes to the owner before any suite or script is written
  the agent's own files declare exactly the systems the architecture
    record names; a commitment the record asked is the owner's to
    answer, and is never filled in
  the suite is written from the spec and never from the scripts
  no test is edited to make a script pass, and no script is delivered
    that the suite fails
  only scripts delivered by a feature's run are packed; a script
    written or changed outside one goes back through a feature's run
  the version is packed only once every feature's run has closed
  nothing is deployed without the owner's yes on the package
  a prototype is read as the most exact statement of what was wanted
    and is never shipped as it stands
measures:
  quality gate: no agent is deployed whose conformance check failed,
                or whose package differs from the one the owner approved
  cycle time: none set from the request to the deployed agent's name
  rounds: revisions before the owner approves the spec, and before the
          conformance check passes; each feature's run counts its own
  defects: cases the conformance check failed on the first pass
records:
  spec              - the spec as the owner approved it, the four
                      answers, and who approved it and when
  architecture      - the architecture record, the owner's answers to
                      what it asked, and the version it was carried
                      from when it was carried forward
  features          - each feature's run: the feature, its run, and how
                      it closed; the suite and the delivery are that
                      run's records
  build-record      - the package's address and sha256, and the signed
                      build record
  deploy-decision   - the owner's yes on the package, and when it was
                      given
  deployment-record - the agent's name and the signed deployment record
  evaluation-record - every case confirmed, failed or flagged, signed
                      by the conformance checker
  publish-decision  - the owner's yes and the AgentDoc's address
